# Build decisions

Decisions made while building Hippomem from the plan in [hippomem.md](hippomem.md). The owner asked for the build to run without supervision, so each choice is recorded here with its reason and the options rejected. Any of them can be overturned; the ones that would be costly to undo later are marked **(costly to undo)**.

| # | Date | Decision | Why | Rejected |
|---|---|---|---|---|
| BD-01 | 2026-10-28 | Each phase is built on its own branch and PR. Claude merges its own PRs once ruff, mypy and pytest pass locally; the owner reviews after | Owner asked for an unsupervised build; small PRs keep each step reviewable later | Stacking unmerged PRs for the owner (blocks the build on review) |
| BD-01a | 2026-10-28 | **Revises BD-01.** Merging to `main` is blocked by the permission check in this environment, so PRs are stacked instead: each phase branches from the previous one and its PR targets that branch. The owner merges them in order | Claude can't merge its own PRs here, and should not work around that | Waiting for each merge before starting the next phase (stalls the build) |
| BD-02 | 2026-10-28 | A new `hippomem` package replaces `hippocampus` on main. The proof of concept's code stays on branch `markdown-poc` | The store, scope and lifecycle all change; adapting the markdown code file by file would cost more than rewriting it | Renaming the old package in place and migrating it gradually |
| BD-03 | 2026-10-28 | Keep the repo's conventions: Python 3.11+, dataclasses, module-level functions, no ORM, no DI framework | Matches the existing code and the Improvements.spec conventions | SQLAlchemy or another ORM |
| BD-04 | 2026-10-28 | Store is one SQLite file (stdlib `sqlite3`, WAL mode), schema versioned with `PRAGMA user_version`. Embeddings are float32 BLOBs scanned with numpy **(costly to undo)** | Local proof with no new dependencies; numpy scan is already proven fine to low thousands of records | Postgres + pgvector (needs a service), sqlite-vec (extension to install; add only when scale needs it) |
| BD-05 | 2026-10-28 | Team config is TOML read with stdlib `tomllib`, not YAML | No new dependency | YAML (needs PyYAML) |
| BD-06 | 2026-10-28 | One server process: a Starlette app with MCP over streamable HTTP at `/mcp` and a small JSON API at `/api` for hooks and the CLI, run by uvicorn. Every request carries a bearer token that maps to an actor (engineer, agent or reviewer) | Agents need MCP; hooks and the CLI need plain HTTP calls that are quick and easy to test. One process owns the database | Hooks reading SQLite directly (would not survive going remote) |
| BD-07 | 2026-10-28 | Pin `mcp>=1.25,<2` | The HTTP transport and per-request context APIs used for identity differ in 2.x; supporting both doubles the surface while proving the concept | Keeping the 1.x/2.x shim from the proof of concept |
| BD-08 | 2026-10-28 | Merge reconciliation calls headless `claude -p` behind a single `judge` function; tests replace it with a stub | No extra API key or service; easy to swap for another model later | A direct Anthropic API client (needs a key); a local model (weaker at reading diffs) |
| BD-09 | 2026-10-28 | The per-turn check looks at git state (files changed since the turn started) and the drafts recorded, never at the transcript | Owner ruled out reading transcripts | Reading the turn's transcript |
| BD-10 | 2026-10-28 | Test agents run as `claude -p` in sandbox repos under a scratch folder, with `--setting-sources project --strict-mcp-config` so the owner's own settings, hooks and MCP servers are never loaded, `--max-budget-usd 1.50` per run and $30 for a whole harness run | Isolates tests from the owner's setup and caps spend | A separate `CLAUDE_CONFIG_DIR` (loses login credentials) |
| BD-11 | 2026-10-28 | Git events in the local proof come from git hooks that `hippomem install git-hooks` writes (post-commit, post-merge, post-checkout) plus a `hippomem event` CLI; closing a branch is `hippomem event close` or the stale check | No GitHub dependency for the proof | A GitHub app or webhook (needs hosting) |
| BD-12 | 2026-10-28 | No stop for review after phase 2. Each merged phase is reported to the owner's brain inbox and the build continues | Owner asked for no supervision | Pausing for a schema review |
| BD-13 | 2026-10-28 | Decisions only ever change by accepting a proposal. Every change makes a new **version**; earlier versions stay in `decision_version`. Proposal kinds: `new`, `supersede`, `evidence`, `promote` (explored → decision), `mapping` **(costly to undo)** | One write path keeps provenance (who made it, via which agent, who accepted it) complete, which the audit-trail use case depends on | Editing decisions in place |
| BD-14 | 2026-10-28 | Scope is a ranking signal in search, not a filter: decisions outside the caller's systems score ×0.8 but still come back when they match well. Team-wide decisions are in scope everywhere | In one team, a hard filter costs more in missed matches (e.g. an unmapped folder) than it saves in noise | Filtering results to the caller's systems |
| BD-15 | 2026-10-28 | Acceptance levels: evidence (any reviewer, or auto by rule), standard (reviewer agent or engineer), heavy (engineer; anything superseding or conflicting counts as heavy), scope (an owner of one of the systems; any engineer if the system has no owners). `self_approval = "standard"` in the team config lets a solo engineer accept their own standard proposals | Implements "Who accepts" from hippomem.md; the solo switch is needed because the pilot may be one engineer | Requiring a second engineer even in a one-person pilot (nothing could ever be accepted) |
| BD-16 | 2026-10-28 | Every decision proposal must have a non-empty `why`; every explored record must have a `revisit_if` | A decision without its reason, or a dead end without its expiry condition, is the noise the memory exists to avoid | Optional fields with placeholder text (the proof of concept's `_No alternatives documented._` problem) |
| BD-17 | 2026-10-28 | Admin commands (`init`, `serve`, `actor`, `map`, `config apply`) work on the memory file directly; everything else (`query`, `review`, `accept`, `show`, `list`) goes through the server with the caller's token | Admin work happens where the server runs; client commands must behave the same once the server is remote | Every command over HTTP (needs a bootstrap admin endpoint) |
| BD-18 | 2026-10-28 | MCP runs stateless with JSON responses. Tools take `repo`, `branch` and `path` as arguments, which the session digest tells the agent, instead of the server tracking MCP sessions | Each call is independent and easy to test; MCP clients can't put per-session values in static headers | Stateful MCP sessions keyed to Claude Code sessions |
| BD-19 | 2026-10-28 | DNS-rebinding protection stays on; only the configured host, 127.0.0.1 and localhost are allowed | A local server on a developer machine is reachable from browser pages; this blocks that | Turning the protection off to simplify tests |
| BD-20 | 2026-10-28 | Tokens are `hm_` + 24 random bytes; only the SHA-256 hash is stored. A coding agent uses its engineer's token and names itself in `X-Hippomem-Agent` | Keeps provenance as "engineer via agent" without issuing per-agent credentials in the proof | Per-agent tokens for coding agents (more setup per engineer) |
